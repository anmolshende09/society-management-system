# Canonical Documentation & Engineering Governance

## 1. Purpose & Core Governance Philosophy

To prevent architectural drift, cognitive overload, and chaotic hallucination across AI-assisted engineering cycles, this repository enforces a strict, two-tier documentation model:

```
┌────────────────────────────────────────────────────────┐
│ CANONICAL DOCUMENTS (Authoritative, Normative)          │
│ • specs.md (Technical baseline & requirements)         │
│ • AGENTS.md (Operating constitution & hard rules)      │
│ • docs/canonical/*.md (Architecture, RLS, Finance)     │
│ • docs/adr/*.md (Architectural Decision Records)       │
│ • docs/compliance/*.md (G-FIN, G-DPDP registers)       │
└────────────────────────────────────────────────────────┘
                          │ Governs & Constrains
                          ▼
┌────────────────────────────────────────────────────────┐
│ NON-CANONICAL / LIVING DOCUMENTS (Working State)       │
│ • docs/plans/*.md (Feature designs and execution plans)│
│ • docs/context/*.md (current-state, active-task, etc.) │
│ • docs/runbooks/*.md (Operational recovery procedures) │
└────────────────────────────────────────────────────────┘
```

---

## 2. Canonical vs. Non-Canonical Taxonomy

### 2.1 Canonical Documents (The Immutable Baseline)

- **Status**: **Normative and Authoritative**. All code, schemas, and configurations MUST conform to these documents.
- **Change Policy**: Immutable during routine development. Changes require an approved Architecture Decision Record (ADR) in `docs/adr/` and explicit project owner approval.
- **Inventory**:
  1. `specs.md`: Master technical specification baseline (domain models, modules, DAG, release gates).
  2. `AGENTS.md`: Agent Operating Constitution and non-negotiable laws.
  3. `docs/canonical/architecture-blueprint.md`: Monolith structure, module boundaries, layer DAG.
  4. `docs/canonical/tenant-security-model.md`: PostgreSQL RLS, role privileges, trusted context model.
  5. `docs/canonical/financial-engineering-rules.md`: Integer paise Money math, immutability, Gate G-FIN.
  6. `docs/canonical/data-dictionary.md`: Schema, tables, composite constraints, audit invariants.
  7. `docs/canonical/api-contract-standards.md`: Uniform JSON wrapper, error codes, string serialization.
  8. `docs/adr/ADR-*.md`: Historical, immutable architectural decisions.
  9. `docs/compliance/finance-review-register.md`: Statutory finance & controller signoff registry.
  10. `docs/compliance/dpdp-register.md`: Personal data inventory, consent, and retention schedules.

### 2.2 Non-Canonical / Living Documents (The Working State)

- **Status**: **Informative, Living, Ephemeral**. Used for coordination, task tracking, and session handoffs.
- **Change Policy**: Updated continuously as tasks progress. Must contain verified facts only; no speculation.
- **Inventory**:
  1. `docs/plans/YYYY-MM-DD-<feature>-design.md`: Feature design document generated by `brainstorming`.
  2. `docs/plans/YYYY-MM-DD-<feature>-plan.md`: Step-by-step execution roadmap generated by `writing-plans`.
  3. `docs/context/current-state.md`: Branch, commit, active milestone, verified commands.
  4. `docs/context/active-task.md`: Current active task, files touched, red/green evidence.
  5. `docs/context/pending-work.md`: Prioritized backlog with blockers.
  6. `docs/context/known-issues.md`: Defects, reproduction steps, workarounds.
  7. `docs/context/next-steps.md`: Immediate next priority.
  8. `docs/runbooks/*.md`: Step-by-step operational and disaster-recovery runbooks.

## 3. High-Signal Engineering & Noise Suppression

To maintain extreme focus and prevent context bloat:

1. **Hard Design Gate**: No code may be written until an approved design exists in `docs/plans/` (`brainstorming`).
2. **The Iron Law of TDD**: No production code without a failing test first (`test-driven-development`).
3. **No Fluff or Narrative Filler**: Avoid pleasantries, speculative commentary, and echoing user instructions. Emit dense, structured, actionable Markdown and terminal evidence.
4. **Evidence-Based Completion**: Never claim a task or check is done without providing the exact command executed, exit code, and terminal output summary (`verification-before-completion`).
5. **Session Continuity**: Every session MUST update `docs/context/current-state.md` and `docs/context/active-task.md` with verified facts before terminating.

## 4. Dynamic Knowledge Protocol (Online Research Rules)

When external information is needed (e.g. library releases, PostgreSQL extensions, fast-changing Node.js/Next.js APIs, legal notifications), **agents must NEVER rely on stale memory or hallucinate**.

### 4.1 Permitted Credible Sources

Online searches MUST be restricted to authoritative, primary sources:

- **Official Documentation**: `postgresql.org`, `nodejs.org`, `nextjs.org`, `orm.drizzle.team`, `redis.io`, `fastify.dev`, `docs.nestjs.com`, `aws.amazon.com`.
- **Official Source Repositories & Releases**: `github.com/<official-org>/<official-repo>`.
- **Statutory / Legal Portals**: `egazette.gov.in` (DPDP Rules), `cbic.gov.in` (GST circulars), `incometax.gov.in` (TDS rules).
- **Standards & Specifications**: `rfc-editor.org`, `openapis.org`, `w3.org`.
- **Established Engineering Publications**: Martin Fowler (`martinfowler.com`), AWS Architecture Blog, Shopify Engineering.

### 4.2 Forbidden Sources (Noise & Hallucination Suppression)

- SEO content farms (GeeksforGeeks, TutorialsPoint, Baeldung, random Medium articles, Dev.to listicles).
- Unverified community forum snippets or outdated StackOverflow answers (check against official docs).
- Speculative AI-generated summaries without direct official citations.
